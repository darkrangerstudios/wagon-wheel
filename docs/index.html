Circle the wagons.

One room where you and your local coding agents work the same problem in the same conversation. Named Claude Code and Codex seats ask each other for help through a typed request and bring the answers back on their own, without you relaying or typing “continue”.

View on GitHub How it's built

Uses your own Claude Code and Codex CLIs, signed in to your own subscriptions. No server, no API keys to paste, no open ports.

How it works

Wagon Wheel is a VS Code extension. It starts each seat's Claude Code or Codex as its own private child process and sits between them, deciding who hears what.

Teamwork

They ask each other directly

You talk with @claude, @codex-2 or @all. The agents ask each other through a typed request tool, not by writing names in their replies. The room delivers each request once and brings the answer back to whoever asked, with no “thanks, got it” turns in between. Text in a reply is never treated as an instruction to the room.

Tasks

A task card, with limits you set

When the agents start working together, a task card shows the goal, who leads, open requests, and the turns and minutes used. Choose Economy, Balanced or Thorough, or set your own limits. Pause, Resume and Stop work at any point. The lead can close the task only when every request has been answered. Limits count turns and time; token use is reported after each turn, so there is no hard token cap.

Participants

One screen to start a room

Pick up to six agents, name them, and choose each one's model and folder. Two can use the same app: a Builder and a Checker both on Codex. Each card shows whether that app is ready, and each agent can start fresh or pick up one of your Claude or Codex conversations, as a copy that leaves your original untouched.

Memory

Your sessions, your choice

Each seat works in a real Claude Code session or Codex thread on your machine: start a new one, fork an existing one (the original stays untouched), or continue one after a warning. You can also let the agents read earlier local sessions, from either tool, as reference: pick a session, choose whether they see its whole history or only what is said from now on, and remove it at any time. Local sessions only. Cloud sessions stay in each provider's own tools.

Context

Everyone stays caught up

Each agent receives exactly what it missed since its last turn, labelled by speaker, and never its own words back. Agent text always arrives marked as relayed, so neither model mistakes the other for you.

Usage

Three views of cost

Your account limits from each provider, this computer's tokens across every local Claude Code and Codex session (with a breakdown by model, subagents, thinking, cache tier and tool call, read from the CLIs' own logs with no model call), and each task's reported turns.

Visibility

Watch them work

Live status for each agent: thinking, the file it's reading, the command it's running, then writing, with a timer. The thinking text is one click away, and every answer keeps its trail of steps.

Files

Bring your files

Paste a screenshot, drop in a log, attach a spec. Images reach the agents as real image input; Markdown, code and data are read inline; PDFs and big files are passed for the agents to open. Whoever missed them gets them on their next turn.

Security

No open ports

The agents talk to the room over stdio, private pipes with no address to dial: no daemon, no localhost port, no web server. Their model requests still go to Anthropic and OpenAI, as they always do. Agents are read-only unless you let one of them edit: then every edit and command appears in the room as an Allow or Deny card, and nothing is pre-approved. Claude's file tools stay confined to its folder; Codex keeps a read-only sandbox, and a command you allow runs outside it. The room blocks quota-credit spending, logout and deletes outright.

How it's built

The chat window talks to the Wagon Wheel core in the VS Code extension host. The core drives one private child process per seat over stdio, reads each seat's saved session from disk when you allow it, and lets nothing listen on a port.

How work moves between agents

You mention; agents request
@claude, @codex-2 or @all deliver immediately. A message with no mention goes to the lead you picked. Agents reach each other only through request_assistance.
Deltas, not transcripts
Each seat keeps its own session; the room sends only the new, labelled lines. A busy agent's queued messages merge into one delivery.
Allowances, not hope
A task has turns and minutes. Accepted requests reserve their answer turn, the last turns are kept for wrapping up, and Pause, Resume and Stop apply to the whole task. Stop is a clean interrupt on both CLIs.
Your conversations, your choice
Start fresh, work on a copy of a conversation you already have, or keep going in the original. Earlier conversations from either app can be shared as read-only reference, whole or only from now on, and revoked.

Cheap to keep talking

Each seat keeps one long-lived session, and the room sends only new lines. Project instructions load once; after that, earlier context is re-read from the provider's prompt cache at a fraction of the price. Here are the same four turns on Claude Sonnet, both ways:

Why not the shared daemon

Codex ships a shared app-server daemon on a Unix socket. It works: other clients see a turn's events live. But it's built for remote SSH and mobile clients, and OpenAI's desktop app deliberately refuses to attach to it locally. When someone forces that, the app's built-in tools break (openai/codex#47425).

Guardrails

  • Codex runs with a read-only sandbox and approvals set to never; web search, connected apps, plugins, hooks and subagents are off for the room process, and every inherited MCP server is explicitly disabled. The room checks the returned settings before admitting a thread.
  • Claude runs with --restricted and --tools Read,Glob,Grep, so your own allow rules cannot widen the room, in dontAsk mode, with --strict-mcp-config allowing only the in-process room server. Verified against the real CLI: the session exposes exactly those three tools plus the three room tools, and a shell attempt is refused.
  • Typed tools are requests, not authority: the room stamps who asked, under which task, and decides admission. A tool call cannot widen permissions, refill an allowance, or resume paused or stopped work.
  • A hard blocklist on protocol methods: spending a rate-limit reset credit, logout/login and thread delete.
  • Model output is untrusted. The webview renders it as text only, with a nonce'd script and no network.

Get started

Wagon Wheel is an early prototype and isn't on the VS Code Marketplace yet. Each release ships an installable .vsix. Tested on macOS; Linux is untested and Windows isn't supported yet.

  1. Have your CLIs signed in

    Install Claude Code, the Codex CLI or both, and sign each in to your own subscription. Wagon Wheel uses them as-is and never installs or signs in anything for you.

  2. Install the extension

    Download wagon-wheel-0.8.1.vsix from the latest release, then install it from the Extensions view (⋯ → Install from VSIX…) or a terminal:

    code --install-extension wagon-wheel-0.8.1.vsix

  3. Start a room

    Click the wheel icon in the Activity Bar and choose Start a Room, or use the wheel button in the editor title bar or Wagon Wheel in the status bar. One screen shows whether each app is ready, lets you bring in conversations you already have, and explains every choice in plain English. A short walkthrough is under Help → Welcome. Set wagonWheel.userName if the agents should know you by a different name.

  4. Tell us what broke

    Wagon Wheel: Report a Problem opens a prefilled GitHub issue with versions and your room's seats and models. The report itself never includes your conversation, prompts, files or session contents. Log lines are optional and shown to you first, and nothing is sent until you submit it. Prefer to build from source? Clone the repo and run code --extensionDevelopmentPath="$PWD/wagon-wheel".

Open questions

  1. Context cost. Both CLIs load the project instruction files from the working folder on every session. Should a room get a slim working folder of its own?
  2. Approvals. Giving a seat write or shell access means routing approval requests to the human in the room. What should that card look like, and what is denied when nobody answers?
  3. More agents. ACP agents such as Gemini CLI run under their own permissions, not the room's. What confinement is honest to claim before enabling them by default?
  4. Shipping it. A .dmg/.exe would keep the same core and swap the shell. Electron or Tauri passes messages internally, so it still needs no port.
